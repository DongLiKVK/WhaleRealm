## 1. 结论先说

**改动前**：站内 6716 条插件条目、14 个空版块、二创作品墙全部没有任何审核状态；四处「举报」按钮点击后只弹一个 toast，从未落到任何人手里。也就是说，侵权、恶意代码、信息失实的通知**没有接收通道**，而页面上写着「24 小时内处理」。
**这不是内容违法，而是无法举证已尽管理义务** —— 一旦被投诉或被问询，拿不出任何一条处理记录。

**改动后**：

## 2. 改动清单（按合规意义分组）

### 2.1 举报通道：从「前端假承诺」到「可追溯的记录」

| 位置 | 改动 | 为什么 |
|---|---|---|
| `server/src/schema.sql` | 新增 `reports` 表（14 列 + 2 索引） | 举报的价值是「可追溯 + 可统计 + 有处理时限」。进邮箱就查不出「处理了没有、谁处理的、结论是什么」，而这些正是被问询时要当场拿出的东西 |
| `server/src/routes/reports.js`（新增） | `POST /api/reports` | 公开可提交（`optionalAuth`），不强制注册 —— 一个还没账号的作者也应该能把自己被搬运的作品报上来 |
| 同上 | 限流 5 次 / 10 分钟 + 同 IP 同目标 600 秒去重 | 举报是低频动作；脚本会把它当免费写入口。去重不拒绝而是返回原编号，避免用户以为「上次没提交成功」 |
| 同上 | `targetType` 五类白名单、`reason` 四类白名单、`detail`≤1000、`contact`≤120 | 目标必须真实存在（逐类型查表，不拼表名），否则举报表会被垃圾灌满，真举报淹没在噪声里 |
| `js/app.js` | 举报面板加「补充说明」「联系方式」两个可选输入；`rpsend` 改为真实请求 | 只有四个固定按钮时，处理人拿到的信息只有「有人说这包有问题」，既没法判断也不够留档 |
| `js/app.js` | 另外四处演示举报按钮去掉「24 小时内处理」这类无后端支撑的承诺 | 页面上的承诺一旦兑不了，比不写更伤信任 |

**`reports` 表为什么用多态两列而不是外键**：举报对象可能是插件 / 动态 / 主题 / 回复 / 用户五类，任何一类都可能是「即将被删除」的那一条。外键级联会让举报记录跟着对象一起消失 —— 恰恰在删掉内容的那一刻，举报记录最该留存。对象删了，举报行还在，后台列表显示「对象已删除」。

### 2.2 审核状态机：从「只有文案」到「能改状态」

| 位置 | 改动 | 为什么 |
|---|---|---|
| `server/src/schema.sql` | `plugins` 表加 `status` / `review_note` / `reviewed_by` / `reviewed_at` | 条目库是本站最大的一块内容（6700+ 条），它的「上/下架」就是审核状态本身 |
| `server/src/db.js` | `migrate()` 内补这四列 + `idx_plugins_status` | `schema.sql` 是 `db.exec` 直跑、**没有 try/catch**，把 `ALTER TABLE` 写进去会让任何老库直接起不来。所以存量库靠 migrate 补，新库由 schema 建 |
| 同上 | 四列默认值 `published` | 6700 多条存量条目是已经在展示的目录数据，补列时不能一次性打成「待审核」—— 那会让整站条目库当场消失 |
| `server/src/routes/forums.js` | `GET /plugins` 加 `WHERE status='published'` | 若把过滤留给前端，被下架的条目仍然出现在 JSON 里，等于没下架 |
| `server/src/routes/forums.js` | `pluginShape` 透传 `status` | 条目页要在已下架时换成说明页，而不是继续给下载入口 |
| `js/app.js` | `entryPage` 增加非 `published` 拦截，新增 `entryHidden` 三态文案页 | 链接会被分享、被搜索引擎收录，直接访问 `#/plugin/<id>` 是真实路径；只在列表里隐藏 = 分享出去仍能取包 |
| `admin/js/page-plugins.js`（新增） | 五态 tabs、关键词/分类/排序、批量上架/驳回/下架、抽屉内写理由 | 误点一次等于把一个真实项目的入口从站上摘掉，所以单条改状态要走理由输入 |

**为什么下架不物理删除**：条目是索引数据（`slug` / `stars` / `license` 都指向真实第三方仓库）。物理删除后同一 slug 重新提交会撞 `UNIQUE`；而下架只需要它在公开面消失，行本身要留着做审计与恢复。

### 2.3 处理闭环：从「举报」到「下架」一步到位

| 位置 | 改动 | 为什么 |
|---|---|---|
| `server/src/routes/admin-reports.js`（新增） | `GET /reports`（五态 + 对象类型筛选 + counts） | 列表默认按时间倒序而不是按状态分组 —— 举报是「先到先处理」的工作，堆积本身就是要看的信号 |
| 同上 | `PATCH /reports/:id`（status + 处理说明≤500） | 监管或作者回访时，这条说明就是处理依据 |
| 同上 | `POST /reports/:id/hide-target` | 把「处理举报」和最要紧的那个动作合成一步，并把下架原因反写进插件的 `review_note` —— 作者申诉时不用在两张表之间对时间线 |
| `admin/js/page-reports.js`（新增） | 抽屉里三个状态键 + 「下架这个插件条目」（二次确认） | 单独按钮而不是列表行内，因为一次误点会直接改公开面 |

**`hide-target` 只对插件生效**：动态的审核状态是另一套语义（`pending` 表示待审，不是下架）。所以其它类型只把举报标记为已处理，不假装删掉了东西。

### 2.4 页面披露：备案号的唯一落点

## 4. 部署与回滚

### 4.1 部署

```bash
# 全量（前端 + nginx 安全头 + 证书）
HOST=158.247.215.153 DOMAIN=whalerealm.top \
  KEY=~/.ssh/jingyu_ed25519 bash deploy/overseas/deploy.sh frontend

# 只发后端（代码上传 + npm ci --omit=dev + systemctl restart + 健康检查）
HOST=158.247.215.153 DOMAIN=whalerealm.top \
  KEY=~/.ssh/jingyu_ed25519 bash deploy/overseas/deploy.sh backend
```

本次实际执行方式：手工 `tar` 上传 `server/src` 与 `dist`（`assets` + `index.html` + `build-manifest.json` + `admin/` + `favicon.ico` + `csp-hashes.json`），`whale/` 从 `dist.old.*` 本地 `cp -a` 恢复以避免重传 60 MB 素材。

> **打包陷阱（本次踩过）**：只 tar `assets + index.html + build-manifest.json` 会漏掉 `admin/`、`whale/`、`favicon.ico`、`csp-hashes.json`，线上后台与鲸鱼页会直接 404。完整清单见 `dist/` 目录。

### 4.2 回滚

| 对象 | 回滚方式 |
|---|---|
| 数据库 | `sudo cp /var/backups/jingyu/pre-compliance-20261029-084030.db /var/www/jingyu/server/data/jingyu.db`（先 `systemctl stop jingyu`） |
| 后端代码 | `/tmp/server-src-old-<时间戳>` 是本次替换前的 `src`，`cp -a` 回去再重启 |
| 前端产物 | `/var/www/jingyu/dist.old.1792956712` 及更早的 `dist.old.*` 都是完整旧产物 |

**三条硬规矩**：
1. **不要用 `scp` / `rsync` 覆盖生产 `.db`**。WAL 里未 checkpoint 的事务会丢，进程还在写会拿到半截库。备份只能用 `better-sqlite3` 的 `backup()` 或 `sqlite3 .backup`（本次用的是后者）。
2. **两台机器不要各自随机 `JWT_SECRET`**，否则每次重启会踢掉全部会话。
3. **不双向同步 SQLite**。两台同时读写同一个库文件，最后一定是某台的写入被静默丢弃。

## 5. 必须由你本人操作的三件事

这三件我这边做不了，原因写清楚：

### 5.1 给 `seekbbs.cn` 加 A 记录（DNSPod 控制台）

**现状**：`dig +short seekbbs.cn` 只返回 NS（`alcohol.dnspod.net` / `coat.dnspod.net`），**A 记录为空**，`www` 也没有，全网不可解析。
**为什么我做不了**：本机与两台服务器上都没有 DNSPod API 凭据（`grep` `/etc` 与 `/var/www/jingyu/server/.env`，`secret_id` / `SecretId` / `tencentcloud` / `DNSPOD` 全部 0 命中；`tccli` 未安装）。
**要做什么**：DNSPod 控制台 → `seekbbs.cn` → 记录管理 → 添加 A 记录：主机记录 `@` 与 `www`，记录值 `43.142.153.74`，线路「默认」。TTL 建议 600（先用小 TTL 便于回滚）。

### 5.2 放行 443（腾讯云轻量控制台安全组）

**现状**：服务器本机 `curl -sk https://127.0.0.1/healthz` = **200**，`ss -lntp` 显示 nginx 正在 `0.0.0.0:443` 与 `[::]:443` 监听，`ufw status` 已 `ALLOW 443/tcp`；但从本机、从境外机、从境内机自己外网访问 **全部超时**（`/dev/tcp` 连不上）。
**为什么我做不了**：拦在云平台防火墙层，本机改 iptables 无效。
**要做什么**：腾讯云轻量应用服务器控制台 → 防火墙 → 添加规则：`TCP:443` 允许 `0.0.0.0/0`。现有规则里只有 22 与 80。

### 5.3 签发 `seekbbs.cn` 证书

**现状**：`certbot` 未安装；`/etc/letsencrypt/live/` 为空；443 目前用自签证书（`CN=43.142.153.74`）只服务 DSH 隧道。
**为什么必须等前两件**：HTTP-01 验证要求域名解析到本机且 80 可达；HTTPS 对外需要 443 放行。
**要做什么**（前两件生效后）：

```bash
sudo apt install -y certbot
sudo mkdir -p /var/www/certbot
sudo certbot certonly --webroot -w /var/www/certbot \
  -d seekbbs.cn -d www.seekbbs.cn --agree-tos -m <你的邮箱> --non-interactive
```

签完后把 `jingyu-443.conf` 的自签路径换成 `/etc/letsencrypt/live/seekbbs.cn/`，并把「除 `/healthz` 与 DSH 隧道外一律 301 回 HTTP」改成正常提供站点。
