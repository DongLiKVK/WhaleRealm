# A 方案落地记录 · 境内唯一写入源，境外降为静态镜像

> 2026-10-29。承接「内容违规评估」的 A 方案：单站境内、境外只做冷备与素材镜像。

## 1. 最终形态

| 节点 | 角色 | 地址 | 写入 | 服务 |
|---|---|---|---|---|
| 境内 | **唯一生产** | `seekbbs.cn` → `43.142.153.74` | 是（唯一写入） | 全站 + 后台 + API + WS |
| 境外 | 静态镜像 + 冷备 | `whalerealm.top` → `158.247.215.153` | 已停用 | 只 301 与返回 503 |

### 境外现在的确切行为

| 路径 | 响应 | 说明 |
|---|---|---|
| `/` | `301 → http://seekbbs.cn/` | 首页整站跳转 |
| `/admin/` | `301 → http://seekbbs.cn/admin/` | 后台同上，老书签仍可用 |
| `/api/*` | `503 {"code":"MOVED"}` | 明确告知已迁移，不再给半可用响应 |
| `/ws` | `400` | 私信端点已迁走 |
| `/assets/*` | `200` | 静态资源保留，作为冷备 |
| `/whale/*` | `200` | 60MB 素材保留 |

**为什么 301 目标先写 `http://` 而不是 `https://`**：443 还没在腾讯云安全组放行，`https://seekbbs.cn` 现在连不上。跳到一个打不开的地址比不跳更糟。等 443 开了再改回 https（见第 5 节）。

## 2. 为什么没有做「境外反代境内」

我先试了这条路，实测数据否掉了它：

```
境外 → 境内裸连 /api/healthz
  connect=1.149s   ttfb=1.377s   total=1.377s   (10 次均值)
境外 → 境内（Host: seekbbs.cn，6 次）
  ttfb_avg=1.473s
境外本地后端（改造前）
  ttfb ≈ 0.93s
```

反代比本地还慢约 0.5 秒 —— 给海外用户多加一跳跨境链路，纯粹负收益。

**还有一个更硬的阻塞**：境内机在腾讯云入口层按「未备案域名」拦截 `Host: whalerealm.top`，返回 `302 → dnspod.qcloud.com/static/webblock.html?d=whalerealm.top`。同一台机器上：

```
Host: whalerealm.top  → 302（被腾讯云拦）
Host: seekbbs.cn      → 200 正常
Host: 43.142.153.74   → 200 正常
```

这说明拦截发生在云平台公网入口（不是 nginx、不是应用层）。反代必须改写 Host 头才能过，而改写 Host 又会破坏 cookie domain 与 CORS 判断。两条都不可接受。

## 3. 为什么敢把境外后端直接停掉

停之前确认了三件事：

1. **数据不会分叉** —— 境内库是境外库的一致性快照（`sqlite3 .backup` + 只搬业务表，跳过 README 抓取缓存两表），两台是两个不同物理文件，不存在同文件并发写。
2. **用户不会丢登录态** —— `JWT_SECRET` 与 `ADMIN_TOTP_KEY` 两台完全一致（实测前缀相同）。若不一致，境内后台的 2FA 密文解不开，站长会被自己锁在门外。
3. **前端不含硬编码绝对域名** —— `assets/api.a6fdfb08.js` 里是 `(window.DSH_API_BASE || '') + '/api'`，相对路径。用户被 301 到 seekbbs.cn 后，API 请求自动打到境内。

## 4. 顺手补上的一个硬缺口：备份

境内成为唯一写入源后，发现 `jingyu-db-backup.timer` 处于 **disabled**。备份脚本 `jingyu-db-backup.js` 一直都在（用 better-sqlite3 的 backup API 做在线热备，不碰 WAL 一致性），只是没被启用。

```bash
sudo systemctl enable --now jingyu-db-backup.timer
sudo systemctl start jingyu-db-backup.service   # 立刻验证真能出备份
```

实测输出：

```
备份完成 jingyu-20261029-171859.db 源=5672960B 产物=5677056B 耗时=53ms
保留 1 份（hourly<=24 daily<=14）
```

保留 hourly 24 份 + daily 14 份的两层策略：前者覆盖「几小时内手滑删了数据」，后者覆盖「一周后才发现数据不对」。产物在 `/var/backups/jingyu/db/`，root:root 0600。

## 5. 还差的一步（必须你在腾讯云控制台做）

**放行 TCP 443**：轻量应用服务器 → 防火墙 → 添加规则 `TCP:443` 允许 `0.0.0.0/0`。

现在的事实：本机 `ufw` 已 `ALLOW 443`、`nginx` 已在 `0.0.0.0:443` 监听、本机 `curl -sk https://127.0.0.1/healthz` = 200，但公网 `/dev/tcp/43.142.153.74/443` **超时** —— 拦在控制台。

放行后按顺序做三件（顺序不能反）：

```bash
# ① 签证书（certbot 已装好 1.21.0）
ssh ubuntu@43.142.153.74
sudo mkdir -p /var/www/certbot
sudo certbot certonly --webroot -w /var/www/certbot \
  -d seekbbs.cn -d www.seekbbs.cn --agree-tos -m <你的邮箱> --non-interactive

# ② 境内 jingyu-443.conf：自签证书换成 LE，并把「一律 301 回 HTTP」改成正常服务

# ③ 两处 SITE_ORIGIN 改回 https 并重启
#    境内：/var/www/jingyu/server/.env
#    境外：把 301 目标从 http:// 改回 https://
sudo sed -i 's|return 301 http://seekbbs.cn|return 301 https://seekbbs.cn|g' \
  /etc/nginx/sites-available/jingyu.conf   # 在境外机
sudo nginx -t && sudo systemctl reload nginx
```

**顺序为什么不能反**：若先把 `SITE_ORIGIN` 改成 https 而 443 不可用，cookie 会带 `Secure` 标志，浏览器在 HTTP 下直接丢弃 —— 症状是「登录成功、刷新变游客」，比直接打不开更难排查。

要让境外重新接管：

```bash
sudo cp /root/pre-mirror-20261029-091916/jingyu.conf /etc/nginx/sites-available/jingyu.conf
sudo systemctl enable --now jingyu
sudo nginx -t && sudo systemctl reload nginx
```

> 注意：回滚境外后，境内这段时间产生的写入不会自动回流。回滚前先导一次境内库。
