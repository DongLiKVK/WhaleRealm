# HTTPS 上线记录 · 2026-10-29

> 443 放行后的完整操作：签证书 → 启用 443 → 80 跳转 → 改 SITE_ORIGIN → 补 HSTS → 验证续期。

| 项 | 值 |
|---|---|

| 证书 | Let's Encrypt，`CN=seekbbs.cn`，issuer `Let's Encrypt / YR2` |

| 80 端口 | `301 → https://seekbbs.cn/`（ACME 路径除外） |

| 续期 | `certbot.timer` 已启用；`--dry-run` 输出 `Congratulations, all simulated renewals succeeded` |

## 2. 执行顺序（顺序本身是设计的一部分）

```
1) 确认 443 公网可达（/dev/tcp 43.142.153.74/443 → OPEN）
2) 准备 ACME 目录并用公网验证：http://seekbbs.cn/.well-known/acme-challenge/probe → 200 acme-ok
3) certbot certonly --webroot -w /var/www/certbot -d seekbbs.cn -d www.seekbbs.cn
4) 改 jingyu-443.conf：自签证书 → LE 正式证书，并让 443 正常服务（不再 301 回 HTTP）
5) reload nginx，用 curl 不加 -k 验证证书被真实信任
6) 改 jingyu-80.conf：整站 301 到 https，但**保留** ACME location
7) 改 .env：SITE_ORIGIN=https://seekbbs.cn，restart jingyu
8) 补 HSTS 到 security-headers.conf
9) 装 reload 钩子 + 跑 --dry-run 验证续期
```

**为什么必须先做 4/5 再做 7**：若先把 `SITE_ORIGIN` 改成 https 而 443 还不能提供服务，cookie 会带 `Secure` 标志，浏览器在 HTTP 下直接丢弃 —— 症状是「登录成功、刷新变游客」。这类半可用状态比直接打不开更难排查。

**为什么 80 不能全站 301**：certbot 的 webroot 验证要访问 `http://seekbbs.cn/.well-known/acme-challenge/<token>`。若 80 一律 301 到 https，一旦某天 443 出问题（证书过期或 nginx 起不来），续期会跟着失败，形成「证书过期 → 无法续期」的死锁。所以 ACME 路径走 HTTP 直出。

**为什么 HSTS 不写 preload**：preload 一旦进浏览器内置列表几乎无法撤销。等确认长期可用再考虑。

## 4. 一个差点漏掉的运维细节

续期成功后 **certbot 不会自动 reload nginx** —— nginx 会一直端着旧缓存里的证书，直到有人手动 reload。表现是「证书明明续了，浏览器still 报过期」。

修法是 deploy 钩子：

```bash
sudo mkdir -p /etc/letsencrypt/renewal-hooks/deploy
printf '#!/bin/sh\nsystemctl reload nginx\n' | sudo tee \
  /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh >/dev/null
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

另一件容易误判的事：`certbot renew --dry-run` 会打印 `Non-interactive renewal: random delay of 188.5 seconds` 然后**静默等 3 分钟**。这不是卡死，是 certbot 为避免所有客户端集中请求 CA 而加的随机抖动。本次第一次等待时我一度以为是进程挂住，实际它自己跑完了并输出成功。
