# README 抓取修复记录 · 2026-10-29

> 症状：境内站点打开插件条目页，README 区域一直空白。
> 根因：`raw.githubusercontent.com` 在境内**整段不可达**，而代码的正文通道只走它。

## 1. 故障复现

```
https://seekbbs.cn/api/plugins/15/readme   → 60s 后空响应（nginx proxy_read_timeout 截断）

境内机出网实测：
  https://api.github.com               200  0.29s   ✓
  https://raw.githubusercontent.com    000  11.2s   ✗ 硬超时
  https://github.com                   200  1.73s   ✓
  https://codeload.github.com          301  1.07s   ✓
```

## 2. 根因链

1. `readme-fetch.js` 用 Trees API（`api.github.com`）列目录 → **这一步是通的**。
2. 然后 `fetchOne()` 对每份正文走 `rawBase()` = `raw.githubusercontent.com` → **每份都超时 9 秒**。
3. 一个仓库最多 6 份 README + 5 份规范文档，`mapLimit(3)` 并发 → 累计远超 nginx 的 60 秒读超时。
4. nginx 掐断连接，前端拿到空响应，README 区域留白。

所以不是「某个文件不存在」，而是**每一步都在白等超时**。

## 3. 修法

### 3.1 增加 Contents API 通道，按可达性自动切换

新增 `fetchOneViaApi()`：走 `api.github.com/repos/{owner}/{repo}/contents/{path}?ref=HEAD`，返回 JSON 里的 `content` 是 base64，解码即原文。

### 3.2 raw 可达性探针（进程级 + 10 分钟缓存）

```
探针文件：github/gitignore 的 README（几百字节，必定存在）
探针超时：min(timeoutMs, 5000)
缓存：10 分钟（机房线路会变，raw 恢复后 10 分钟内自动切回）
不可达时打印：[readme] raw.githubusercontent.com 不可达（TIMEOUT），正文通道切到 Contents API
```

为什么不「每次先试 raw 再回落」：raw 的超时是 9 秒，一次请求白等 9 秒不如先探一次（5 秒上限，且一次探完全进程共用）。

### 3.3 通道选择策略

| raw 是否可达 | 首选 | 失败后 |
|---|---|---|
| 可达 | raw（不消耗 API 限额） | Contents API |
| 不可达 | Contents API | raw |

`probeCandidates()`（Trees 不可用时的兜底）同样按这个策略走 —— 否则 16 个候选文件名 × 9 秒 = 两分钟的纯等待。

### 3.4 配额预算：无 Token 时自动收紧

实测每个仓库消耗：Trees 1 次 + 每份正文 1 次。抓满 6 份 README + 5 份规范文档 = **12 次/仓库**。
无 Token 的限额是 **60 次/小时**，只够 5 个仓库 —— 一个访客随手点几下就打满。

所以新增 `budgetFor(token)`：

| 有 Token | maxDocs | maxMeta | 单仓库约消耗 | 每小时覆盖 |
|---|---|---|---|---|
| 否（60/h） | 2 | 1 | 4 次 | ~15 个仓库 |
| 是（5000/h） | 6 | 5 | 12 次 | ~400 个仓库 |

取舍：**宁可少给几份文档，也别让整条功能因为配额用完而全站失效。**

### 3.5 限额耗尽不再伪装成「没有 README」

原先 `res.code === 'RATE_LIMITED'` 会落进「负缓存」分支（`saveReadme(status:'none')`），后果有两个：
1. 前端显示「作者仓库里没有 README」—— 误导，实际是我们自己的配额用完了；
2. 写进负缓存后，这一条在 24 小时内都不再重试，配额恢复也不会自愈。

现在单独分支：

```js
if (res.code === 'RATE_LIMITED') {
  reply.header('Cache-Control', 'no-store');
  return { ok: true, data: { item: { status: 'none', code: 'RATE_LIMITED',
    message: '服务端读取 GitHub 的配额暂时用完了，过一会儿再刷新（不写缓存，恢复后会自动重抓）' } } };
}
```

前端 `js/plugin-page.js` 同步区分：`item.code === 'RATE_LIMITED'` 走 `status:'error'`（可重试），而不是 `status:'none'`（当成不存在）。

## 5. 根治限额：配 GITHUB_TOKEN

限额问题是硬约束，代码只能省着用，不能变多。真正解决要靠 Token：

```bash
# 1) 建一个只读 public repo 的 Personal Access Token（不需要任何 scope，只读公开仓库即可）
#    https://github.com/settings/tokens  → Generate new token (classic) → 不勾任何 scope
#
# 2) 写进服务器 .env（不要写进仓库）
ssh ubuntu@43.142.153.74
sudo sed -i '/^GITHUB_TOKEN=/d' /var/www/jingyu/server/.env
echo 'GITHUB_TOKEN=ghp_xxxxxxxxxxxx' | sudo tee -a /var/www/jingyu/server/.env
sudo chown jingyu:jingyu /var/www/jingyu/server/.env && sudo chmod 640 /var/www/jingyu/server/.env
sudo systemctl restart jingyu

# 3) 验证：限额应从 60 变 5000，且预算自动放宽到全量文档
curl -s https://api.github.com/rate_limit | head -20
```

配好之后 `budgetFor()` 会自动放开到 6 份 README + 5 份规范文档，不需要改任何代码。
