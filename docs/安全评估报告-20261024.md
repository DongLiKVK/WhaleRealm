## 5. 攻击痕迹与入侵判断

### 5.1 判定结论：**未发现入侵证据**

依据：

1. 成功登录记录只有运维方密钥（111.31.187.43），无陌生 IP 登录成功记录
2. 无新增账号、无 uid=0 异常账号、无 sudoers 改动
3. SUID 异常扫描仅系统自带 polkit-agent-helper-1；`dpkg -V` 核心包校验通过
4. 无 `/etc/ld.so.preload`；/tmp、/var/tmp、/dev/shm 无异常可执行文件（仅部署脚本残留）
5. cron / systemd timer 清单干净（certbot、apt、logrotate 等系统项）；linuxuser、jingyu 均无用户 crontab
6. 进程清单无异常（无挖矿、无反弹 shell），对外 established 连接仅本次 SSH
7. 上传目录仅 1 个 webp 文件，无 php/js/html/svg 等可执行/可脚本文件；主机未安装 PHP，webshell 无解析环境
8. 无异常重启（仅 10-05 初始化、10-23 重启），内核 taint=0

### 5.2 观察到的攻击行为（全部被拦截）

- SSH 爆破：17 小时 367 次失败，4 个 IP 在封禁中（详见 3.1）
- 漏洞扫描器 UA：sqlmap / nikto / nuclei 等 11 次
- 敏感文件探测：`.env` 系列约 150 次、`/wp-login.php` 28 次、`/.git/config` 11 次 —— 命中 444/404，未泄露
- 端口扫描：UFW 今日丢弃 1837 个包（DPT 3000/3389/2323/8081/9694/13756/4575…）
- 代理滥用探测：`CONNECT ip.cypher.rest:443`、`GET http://httpbin.org/get`（Go-http-client）—— 被 400 拒绝，说明有人在试探开放代理
- 全站日志量：11 小时 4213 请求，404 1158、444 401、400 102 —— 扫描占比约 40%

## 6. 风险清单

| 编号 | 风险 | 等级 | 依据 | 可能后果 |
| --- | --- | --- | --- | --- |
| R1 | SSH 允许 root + 口令登录，22 端口对全网开放，日均数百次爆破 | **高** | PermitRootLogin yes / PasswordAuthentication yes / 367 次失败 | 口令被猜中即 root 沦陷，站点、数据库、用户数据全失守 |
| R2 | 无 WAF / IDS / HIDS / auditd，fail2ban 只管 sshd | **中高** | 工具链实测全部缺失 | Web 层 0day、上传滥用、撞库只能靠应用自己扛；事后无法取证 |
| R3 | Node.js 20 已 EOL | 中 | 20.x 维护期 2026-04-30 结束 | 运行时漏洞不再修，依赖链风险累积 |
| R4 | 数据库与备份文件权限过宽（0644） | 中 | jingyu.db 644、backup/*.db 644 | 本机任意账号可读全部用户邮箱/哈希/帖子；备份含历史库 |
| R5 | 单源站、无 CDN / 无 DDoS 清洗，HTTP/1.1，worker_connections 768 | 中 | 直连 158.247.215.153，无代理层 | 流量型 DDoS 直接打瘫；L7 洪泛靠 30r/s 单 IP 限流，分布式可绕过 |
| R6 | 缺 HSTS；Server 头暴露 nginx/1.18.0 (Ubuntu)；无 HTTP/2 | 低-中 | 响应头实测 | 首次明文请求可被降级/劫持；版本指纹便于定向选 payload |
| R7 | 上传文件以 inline 提供，类型白名单需确认 | 低 | Content-Disposition: inline | 若放开 svg/html，可能形成同源存储型 XSS（CSP 有缓解） |
| R8 | Ubuntu Pro 未启用，2027-04 后无 ESM | 低（前瞻） | pro status attached=false | 标准支持到期后无安全补丁 |
| R9 | 后台仅 1 个 owner 账号、无 2FA，初始口令是否已改未知 | 中 | admin_accounts 仅 root | 口令泄露 = 后台全权限；建议轮换 + 上 2FA |
| R10 | linuxuser 账号存在且可登录 shell，长期未使用 | 低 | passwd/authorized_keys | 多余攻击面，弱口令即入口 |

## 7. 加固方案

### P0 —— 今天做（30 分钟内，收益最大）

1）关掉 SSH 口令登录与 root 口令登录（保留密钥）

```bash
cat >/etc/ssh/sshd_config.d/99-hardening.conf <<'EOF'
PermitRootLogin prohibit-password
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
EOF
sshd -t && systemctl reload ssh
# 验证：新开一个窗口用密钥登录成功，再关闭旧会话
```

2）fail2ban 加大封禁力度 + 补 recidive（惯犯）与 nginx 限流 jail

```bash
cat >/etc/fail2ban/jail.d/10-hardening.local <<'EOF'
[DEFAULT]
bantime  = 1d
findtime = 1h
maxretry = 4

[recidive]
enabled  = true
logpath  = /var/log/fail2ban.log
bantime  = 1w
findtime = 1d
maxretry = 3

[nginx-req-limit]
enabled  = true
filter   = nginx-req-limit
logpath  = /var/log/nginx/error.log
maxretry = 20
findtime = 5m
bantime  = 1h
EOF
# filter 需存在：/etc/fail2ban/filter.d/nginx-req-limit.conf（匹配 "limiting requests"）
systemctl restart fail2ban && fail2ban-client status
```

3）轮换后台 root 口令（并确认不是初始的 WhaleRoot@2026#7）

```bash
# 用后台「权限管理 → 修改密码」，或服务端脚本重置：
sudo -u jingyu env NEW_PASSWORD='<新强口令>' node /var/www/jingyu/server/scripts/reset-admin-password.js root
```

### P1 —— 本周做

4）收紧文件权限

```bash
chmod 640 /var/www/jingyu/server/data/jingyu.db
chmod 750 /var/www/jingyu/server/data /var/www/jingyu/backup
chmod 600 /var/www/jingyu/backup/*
chown -R jingyu:jingyu /var/www/jingyu/server/data
```

5）处理 linuxuser

```bash
usermod -L -s /usr/sbin/nologin linuxuser   # 或 userdel -r linuxuser
```

6）补齐头部与协议（`/etc/nginx/snippets/jingyu-security-headers.conf` 追加一行，再 `nginx -t && systemctl reload nginx`）

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
```

- `/etc/nginx/nginx.conf` 的 `# server_tokens off;` 去掉注释（同时去掉 `ssl_protocols` 全局里的 TLSv1/TLSv1.1）
- 443 监听改 `listen 443 ssl http2 default_server;`（nginx 1.18 必须用这种写法，不能写 `http2 on;`）
- 加连接数限制：`limit_conn_zone $binary_remote_addr zone=conn_per_ip:10m;` + server 内 `limit_conn conn_per_ip 20;`
- 按需把 `worker_connections 768` 提到 2048–4096

7）Node 20 → 22 LTS

```bash
# NodeSource 22.x 源，装完 systemctl restart jingyu && curl -s localhost:3000/healthz
```

8）依赖体检（每次发版跑）

```bash
cd /var/www/jingyu/server && npm audit --omit=dev
```

### P2 —— 本月做

9）**上 Cloudflare 橙云**（对应你之前问的"橙云"）：把 A 记录改为代理模式，源站 443 只放行 Cloudflare 回源段，开启 WAF 托管规则 + Bot Fight + 速率限制。这样同时解决三件事：隐藏源站 IP、L7 WAF、DDoS 清洗。Vultr 控制台再确认 Firewall Group 是否开启（22 建议只放行你的出口 IP）。
