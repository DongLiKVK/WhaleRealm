# 插件自动审核与自动上架 · 2026-10-29

> 用户要求：设置一个 agent 自动审核，审核完自动上架，把自动化跑通。

## 1. 为什么用确定性规则脚本，而不是让大模型逐条读

这不是偷懒，是四条硬约束：

| 理由 | 说明 |
|---|---|
| **可复现** | 同一批数据跑两次，结论必须一致。模型做不到，判定会漂移 |
| **可审计** | 每条判定都带「命中哪条规则、命中哪个词」，被问询时能当场拿出依据 |
| **零成本** | 6716 条存量 + 每日新增，逐条调模型是持续开销 |
| **服务器上没有模型凭据** | 生产机的 `.env` 只有 JWT / COS / 短信配置，没有任何 LLM API Key |

模型更适合做「规则没覆盖的疑难条目」的二次判断，不适合当第一道闸门。所以架构是：

```
确定性规则（自动）  →  approved 直接上架
                  →  rejected 直接驳回
                  →  manual   留 pending 等人工（规则只擦到边）
```

## 2. 规则设计：为什么必须带「排除词」

第一版只有关键词，跑出来的结果很难看：

| 版本 | 拦截率 | 误杀 |
|---|---|---|
| 纯关键词 | 100% | **55 条（0.82%）** |
| 加排除词 + 拆弱信号 | **100%** | **0 条** |

那 55 条误杀全部是「词对但语境不对」：

| 被误杀的词 | 实际语境 |
|---|---|
| 提权 | DSH 自身的**沙箱提权审批**、Windows **UAC 提权**，是正常功能（17 条） |
| 红队 / pentest / 渗透测试 | 大量**授权安全研究**插件这么写（含 `dsh-pentest`、`helm-d`） |
| 自动轮换 | **壁纸轮播**、皮肤切换也用这个词（18 条账号池误杀里大半是这个） |
| 每日签到 | token 记账**小游戏**用了「签到」作为机制名 |
| 越狱 | 有的插件是用来**检测**越狱（`dsh-defend` 检测提示词注入） |
| 透视 | UI 主题里「磨砂玻璃可**透视**桌面」，不是游戏透视（3 条） |

所以每条规则都加了 `except`：命中排除词则**本条规则不生效**。注意是**逐条豁免**，不是全局豁免——「授权渗透」可以放过 offensive 规则，但不能连 adult 也一起放过。

### 排除词写得过宽的代价（真实踩过）

我把「扫码 / 配对」放进 remote-gateway 的 except 里，结果：

```
拦截率从 100% 掉到 90%
漏放 dsh-remote-mobile :: 远程与移动端安全网关（Tailscale 访问、扫码配对）
漏放 tongailinc-dsh-mobile-access :: 移动端访问网关（扫码访问）
```

因为**这两个词正是远程网关插件的招牌措辞**。修正：except 里只留「描述性动作」（投送 / 还原历史 / 天气定位），去掉「扫码 / 配对」。

## 3. 最终规则表

| 规则 | 级别 | 说明 |
|---|---|---|
| adult | block | NSFW / 色情 / 涩涩 / 成人向；排除「检测/拦截/审核」类用途 |
| overwall | block | 翻墙 / v2ray / shadowsocks / fake-ip / 代理池 / 住宅代理 |
| clash-netcfg | flag | 单独出现的 clash / mihomo / ssr / 梯子（可能是本机网络配置） |
| accountpool | block | **白嫖 / 共享账号 / 凭据续期 / 跨渠道轮换 / 密钥末四位 / 号池** |
| accountpool-weak | flag | 多账号池 / 多账号轮换 / 自动签到（弱信号） |
| offensive | block | 免杀 / webshell / 木马 / 远控 / 撞库 / 社工库 / exploit / ddos；**排除「授权/沙箱/审批/红队评审/CTF」** |
| security-research | flag | 提权 / 红队 / 渗透测试 / 逆向 / 漏洞（安全研究弱信号） |
| gamecheat | block | **Cheat Engine / 游戏内存修改**（无条件拦，不设 except） |
| transparency-ui | flag | 透视 / 内存修改；排除「主题/皮肤/透明/窗口」 |
| gambling | flag | 德州扑克 / 扑克桌 / 筹码 / 博彩 / 彩票 |
| dos | block | ddos / cc 攻击；排除「压测/性能测试/k6」 |
| loadtest | flag | 压测 / k6（弱信号） |
| jailbreak | block | 软破限 / 去除注入 / 绕过审查；排除「检测/防护/审计」 |
| academic-piracy | flag | Sci-Hub / WebVPN / CARSI / 知网全流程 / 校外访问 |
| remote-gateway / proxy-weak / shell-exec / crawler | flag | 弱信号，全部带 except |

**关键教训：`gamecheat` 不能设 except。**
第一版给它加了 `except: /调试/`，结果 `dsh-cheatengine` 的描述「动态内存**调试**…游戏内存修改」因为含「调试」被豁免，直接漏放。游戏作弊的判定不看语境——只要点名 Cheat Engine 或游戏内存修改就是作弊工具。

## 6. 自动化怎么串起来的

一次 `jingyu-sync-awesome.service` = 四步串行，跑完即生效：

```
① 拉取    分块 range 续传 catalog.json（128KB/块，每块 30s，3 次重试）
② 导入    import-awesome.mjs → 新条目一律 pending
③ 审核    review-plugins.cjs → approved 转 published / rejected 转 rejected
④ 汇总    统计剩余 pending 数，写日志 + logger
```

**为什么要串在同一个 service 而不是各挂一个 timer**：两者有依赖（审核必须在导入之后），拆成两个 timer 无法保证顺序，还会出现「导入完还没审、公开面一直旧」的窗口期。

| 对象 | 路径 |
|---|---|
| 同步+审核脚本 | `/usr/local/sbin/jingyu-sync-awesome.sh` |
| systemd service | `/etc/systemd/system/jingyu-sync-awesome.service` |
| systemd timer | `/etc/systemd/system/jingyu-sync-awesome.timer`（每日 04:30，抖动 600s） |
| 审核器 | `/var/www/jingyu/server/scripts/review-plugins.cjs` |
| 日志 | `/var/log/jingyu-sync-awesome.log` |

`Persistent=true` 保证关机错过的在开机后补跑；任何一步失败都不影响已上架内容，失败信息进日志。

## 7. 日常怎么看

```bash
# 待人工复核有多少
sudo -u jingyu node /var/www/jingyu/server/scripts/review-plugins.cjs --dry-run

# 看日志
sudo tail -30 /var/log/jingyu-sync-awesome.log

# 规则改了之后先跑回归，通过再上线
sudo -u jingyu node /var/www/jingyu/server/scripts/review-plugins.cjs --test

# 手动触发一次完整链路
sudo systemctl start jingyu-sync-awesome.service
```

## 8. 已知限制（必须说清）

| 项 | 说明 |
|---|---|
| 规则是黑名单，不是理解 | 描述里**完全不提高危词**的恶意插件拦不住。第一道闸门够用，但不是万能的 |
| 转人工会积压 | 弱信号命中就留 pending，长期会攒下需要人看的条目。当前 6 条 |
| `dsh-whale-loli` 仍在公开面 | 已上架的成人向条目，上一轮整改漏掉，需要单独下架 |
| 每日拉取仍受国内带宽限制 | 4.2MB 分块续传要跨多轮，可能两天才拉完一次全量 |
