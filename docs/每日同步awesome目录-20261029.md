# 每日同步 awesome-dsh-plugin 目录 · 2026-10-29

> 目标：把 [awesome-dsh-plugin.com](https://awesome-dsh-plugin.com/zh/) 收录的插件补进鲸域条目库，每天自动跑一次。

## 1. 为什么能抓、抓什么

对方站提供 **结构化 JSON**，不用解析 HTML：

```
GET https://awesome-dsh-plugin.com/zh/catalog.json
  → 4,203,108 B（约 4.2 MB）
  → { items: [ { slug, name, owner, short, desc, cat, tag, stars, dl, npm, added, href, cmd }, ... ] }
robots.txt: User-agent: * / Allow: /   ← 明确允许抓取
```

两站差异（实测）：

| 项 | 数值 |
|---|---|
| 对方收录 | 7557 条 |
| 鲸域原有 | 6716 条 |
| 简单按 name 比对会得出「缺 1330 条」 | 但这个数字不可靠，见下 |
| **三重判重后的真实缺口** | **629 条** |
| 实际入库 | **605 条成功 / 24 条 slug 冲突** |

## 2. 为什么不能拿 `name` 当唯一键

对方的 `name` 字段有三个坑：

| 形态 | 条数 | 例 |
|---|---|---|
| 含 `#`（monorepo 子包） | **751** | `dsh-web#packages/dsh-skill-explorer` |
| 重复 | **381 个 name** | `dsh-archive-manager` 出现 7 次 |
| 含空格 | 7 | `agent relay` |

直接当 slug 用会污染库。真正的唯一键是 `slug`（`owner/repo` 或 `owner/repo--子路径`，**始终干净、0 条含 `#`**）。

判重走三重，任一命中即视为已有：

```
① 该条目的 repo（https://github.com/owner/repo）是否已在库的 repo 列
② 由 slug 解析出的 owner/repo 是否已作为 slug 存在
③ 由 slug 解析出的 repo 名（小写）是否已作为 slug 存在
```

## 3. 为什么只写 `pending`，不写 `published`

这是第三方目录站的元数据，**没经过我们自己的合规筛查**。

如果直接 `published`，上次整批下架的那 21 条高危条目（成人向、免杀、翻墙代理、白嫖账号池）**会原样灌回公开面** —— 合规整改当场作废。

所以一律进 `pending`，由后台「插件审核」页人工过一遍再上架。

## 4. 拉取通道：为什么必须分块续传

这条是本次最大的技术障碍，实测数据：

| 场景 | 结果 |
|---|---|
| 境外机直连 | **0.58 秒**（4.2 MB 全量） |
| 境内直连，`--max-time 20s` | 只拿到 253,445 / 4,203,108 字节（12.7 KB/s） |
| 境内直连，`--max-time 40s` | 只拿到 666,866 / 4,203,108 字节（16.7 KB/s） |
| 境内直连，`--max-time 60s` | **超时失败** |

一条 curl 无论超时设多少都必然中途断掉。但探测响应头发现两个关键事实：

```
server: GitHub.com          ← 该站是 GitHub Pages 托管
accept-ranges: bytes        ← 支持断点续传
content-length: 4203108
```

所以改成分块续传：每块 512 KB、单块超时 40 秒。单块按 15 KB/s 约 34 秒，正好在超时内。失败自动重试一次，仍未成就保留 `.part` 让下一轮从断点继续。

脚本逻辑：

```
HEAD 拿 content-length
  → 从 0 开始，逐块 curl --range OFF-END
    → 校验拿到字节数 == 期望字节数
      → 追加到 .part，OFF 前进 512KB
    → 单块失败：sleep 5 重试一次
      → 仍失败：中止本轮，保留 .part
  → 全部拉完：JSON 校验通过才 mv 成正式副本
    校验失败：丢弃本轮，保留旧副本（不让坏数据覆盖好的）
```

**关键设计：任何一步失败都保留旧副本。** 宁可今天不更新，也不让站点因为拿到半截 JSON 而读不到条目。

## 5. 定时与部署

| 对象 | 路径 |
|---|---|
| 同步脚本 | `/usr/local/sbin/jingyu-sync-awesome.sh` |
| systemd service | `/etc/systemd/system/jingyu-sync-awesome.service` |
| systemd timer | `/etc/systemd/system/jingyu-sync-awesome.timer`（每日 04:30，随机抖动 600s） |
| 本地副本 | `/var/lib/jingyu-import/awesome-catalog.json` |
| 断点文件 | `/var/lib/jingyu-import/awesome-catalog.part` |
| 日志 | `/var/log/jingyu-sync-awesome.log` |
| 导入脚本 | `/var/www/jingyu/server/scripts/import-awesome.mjs` |

`RandomizedDelaySec=600` 是为了不在整点集中请求对方站；`Persistent=true` 保证关机错过的会在开机后补跑。

## 6. 实测结果

```
首次导入（用已落盘的副本）：
  源条目数      7557
  库内 slug=6716  repo=6674
  待新增        629
  完成：新增 605  跳过 24
  库内合计      7321 条（pending 605）
  PRAGMA integrity_check → ok

第二次跑（同步流程）：
  待新增 0（因为上一轮已入库）
  说明判重生效，不会重复插入
```

那 24 条跳过的原因：`UNIQUE constraint failed: plugins.slug` —— 说明这些包名在库里已被**另一个仓库**占用。这是正常的去重结果，不是失败。典型如 `dsh-subagent-control` 有 3 个不同仓库都叫这个名，只能进一个。

## 7. 怎么核对与审核

```bash
# 看有多少条待审
sudo -u jingyu node -e "
  const D=require('/var/www/jingyu/server/node_modules/better-sqlite3');
  const d=new D('/var/www/jingyu/server/data/jingyu.db',{readonly:true});
  console.log(d.prepare(\"SELECT COUNT(*) n FROM plugins WHERE status='pending'\").get());
"

# 看同步日志
sudo tail -30 /var/log/jingyu-sync-awesome.log

# 手动跑一次
sudo systemctl start jingyu-sync-awesome.service

# 只看会新增多少、不写库
sudo -u jingyu node /var/www/jingyu/server/scripts/import-awesome.mjs --dry-run
```

604 条待审条目在后台 **/admin/ → 插件审核 → 待审核** 页里，可以逐条通过或批量上架。**建议先抽检描述里有没有高危关键词**（免杀、翻墙、白嫖、NSFW），再批量放行。

## 8. 已知限制

| 项 | 说明 |
|---|---|
| 首轮全量要 4–5 分钟 | 分块续传，24 块 × 约 34s，可能跨两轮才拉完（`.part` 会续） |
| 对方站随时可能改结构 | 脚本只依赖 `items[].slug` / `cat` / `tag` / `desc` / `stars`，缺字段不会崩，但分类映射会落到「其他」 |
| 只补新增，不更新已有 | 已存在的条目（三重判重命中）**完全跳过**，不会用对方的 desc 覆盖我们自己的文案 |
| 不抓 README | README 由 `warm-readmes.cjs` 按需抓（7 天 TTL），两条链路互不依赖 |
